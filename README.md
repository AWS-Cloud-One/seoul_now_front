## 작업 위치 알아보기

처음부터 설정 파일을 모두 이해할 필요는 없습니다. 실제 기능을 개발할 때는 **`src/` 안에서 작업**하면 됩니다.

| 하고 싶은 작업                         | 작성할 위치       | 쉽게 말하면                                    |
| -------------------------------------- | ----------------- | ---------------------------------------------- |
| 홈·추천 등 화면 전체 구성              | `src/pages/`      | 한 화면의 배치를 조립하는 곳                   |
| 버튼·카드처럼 여러 곳에서 쓰는 UI 작성 | `src/components/` | 화면을 이루는 작은 조각을 모아 두는 곳         |
| 백엔드에 요청 보내기                   | `src/api/`        | 서버와 데이터를 주고받는 함수                  |
| 조회·위치 등 React 동작 재사용         | `src/hooks/`      | 여러 컴포넌트에서 반복되는 상태·동작을 묶는 곳 |
| 여행 조건·대화·이력 관리               | `src/state/`      | 화면들이 함께 쓰는 상태와 저장 처리            |
| 요청·응답 등 데이터 형식 정의          | `src/types/`      | 데이터에 어떤 항목이 들어오는지 정의하는 곳    |
| 공통 스타일 작성                       | `src/styles/`     | Tailwind 진입점과 공통 CSS                     |

```text
seoul_now_front/
├── public/                 # 이미지 등 그대로 제공할 정적 파일
├── src/
│   ├── api/
│   ├── components/
│   ├── hooks/
│   ├── pages/
│   ├── state/
│   ├── types/
│   ├── styles/
│   │   └── global.css      # Tailwind를 불러오는 공통 CSS
│   ├── App.tsx             # 화면을 연결할 최상위 컴포넌트. 현재는 기본 문구만 표시
│   ├── main.tsx            # React 앱의 시작점
│   ├── test-setup.ts       # 테스트 공통 설정
│   └── vite-env.d.ts       # 환경변수 타입 선언
├── index.html              # 브라우저가 처음 읽는 HTML
├── .env.example            # 환경변수 작성 예시
├── package.json            # 실행 명령과 패키지 목록
├── package-lock.json       # 팀이 공유하는 정확한 설치 버전
├── vite.config.ts          # 개발 서버·경로 별칭·프록시 설정
├── vitest.config.ts        # 테스트 실행 설정
├── tsconfig*.json          # TypeScript 검사 설정
├── eslint.config.js        # 코드 규칙 설정
└── README.md
```

현재 기능별 폴더에는 `.gitkeep`만 있습니다. Git은 빈 폴더를 저장하지 않기 때문에 구조를 유지하려고 넣어 둔 파일입니다. 실제 코드가 생기면 삭제해도 됩니다.

`main.tsx`가 앱을 시작하고 `App.tsx`를 렌더링합니다. 이후 `pages/`에 만든 화면을 `App.tsx`에 연결하면 화면이 나타납니다. `@/`는 `src/`를 줄여 쓰는 경로 별칭입니다. 예를 들어 `@/pages/HomePage`는 `src/pages/HomePage`를 뜻하며, 이 파일은 아직 없습니다.

## 처음 실행하기

### 1. Node.js와 npm 확인하기

이 프로젝트는 **Node.js 24 LTS와 npm 11**을 사용합니다. Node.js의 최소 버전은 24.11.1이며, 다른 메이저 버전은 현재 설치 조건에 포함되지 않습니다.

- **Node.js:** 내 컴퓨터에서 개발 서버와 빌드 도구를 실행하는 환경입니다.
- **npm:** 프로젝트에 필요한 패키지를 설치하고 개발 명령을 실행하는 도구입니다. Node.js 설치 시 함께 제공됩니다.

터미널에서 다음 명령을 실행합니다.

```bash
node --version
npm --version
```

Node는 `v24.x.x`, npm은 `11.x.x`가 나오는지 확인합니다. 명령을 찾을 수 없다는 메시지가 나오면 Node.js 24 LTS를 설치하고 터미널을 다시 열어 주세요.

### 2. 프론트 폴더에서 터미널 열기

VS Code 등에서 **프론트의 `package.json`이 있는 폴더**를 열고 터미널을 실행합니다. 현재 작업 공간의 상위 폴더에서 시작했다면 다음처럼 이동합니다.

```bash
cd seoul_now_front
```

이미 프론트 폴더 안에 있다면 다시 이동하지 않습니다. 별도로 내려받은 저장소는 폴더명이 다를 수 있으므로 이름보다 **`package.json`이 있는 위치인지** 확인하세요. 이후 명령은 모두 이 위치에서 실행합니다.

### 3. 필요한 패키지 설치하기

```bash
npm ci
```

`package-lock.json`에 기록된 버전으로 패키지를 설치합니다. 처음에는 인터넷 연결이 필요하며, 설치 결과는 `node_modules/`에 들어갑니다. 이 폴더를 직접 수정하거나 Git에 올릴 필요는 없습니다.

### 4. 개발 서버 실행하기

```bash
npm run dev
```

터미널에 접속 주소가 표시되면 **[http://localhost:5173](http://localhost:5173)**을 엽니다. 서버가 실행 중인 터미널은 계속 열어 두세요. 실행 중에는 다른 명령을 입력하려고 새 터미널을 열어도 됩니다.

**실행하면 `서울, 지금 어디?` 제목과 짧은 안내 문구가 표시됩니다.** 이후 코드를 작성하면 저장할 때 변경 내용이 반영됩니다. 빨간 오류 화면이나 터미널 오류가 발생한다면 아래 [자주 겪는 문제](#자주-겪는-문제)를 확인하세요.

작업을 마치려면 개발 서버가 실행 중인 터미널에서 `Ctrl+C`를 누릅니다.

## 다음 날 다시 개발할 때

프론트 폴더에서 개발 서버만 다시 실행하면 됩니다.

```bash
npm run dev
```

매번 패키지를 다시 설치하지 않아도 됩니다. 팀원의 변경 사항을 받은 뒤 **`package.json`이나 `package-lock.json`이 바뀌었다면** 먼저 `npm ci`를 실행하세요.

```bash
npm ci
npm run dev
```

`npm ci`는 기존 `node_modules/`를 잠금 파일 기준으로 다시 설치합니다. 직접 작성하는 `src/` 파일은 변경하지 않습니다.

## 패키지와 Node 버전 관리

| 파일                                   | 역할                                         | 수정하는 시점                      |
| -------------------------------------- | -------------------------------------------- | ---------------------------------- |
| [package.json](package.json)           | 사용하는 패키지·개발 명령·Node/npm 허용 버전 | 패키지나 실행 설정을 바꿀 때       |
| [package-lock.json](package-lock.json) | 패키지와 하위 의존성의 정확한 설치 결과      | npm이 패키지 변경 시 자동으로 갱신 |
| [.npmrc](.npmrc)                       | 패키지 버전 고정·실행 환경 검사 설정         | 팀의 설치 규칙을 바꿀 때           |

**`package.json`과 `package-lock.json`은 함께 공유합니다.** 잠금 파일을 손으로 수정하거나 설치 오류를 해결하려고 임의로 삭제하지 않습니다.

새 패키지가 필요하면 사용할 버전을 확인한 뒤 추가합니다. 아래의 `패키지명`과 `버전`은 실제 값으로 바꿔 입력합니다.

```bash
# 앱에서 사용할 패키지
npm install 패키지명@버전

# 검사·빌드·테스트 등에 사용할 개발 도구
npm install -D 패키지명@버전
```

패키지를 추가하는 사람은 `npm install`, 변경 사항을 받는 팀원은 `npm ci`를 사용하면 됩니다.

## 코드 검사와 테스트

코드를 작성한 뒤에는 필요한 검사를 실행합니다.

| 명령                   | 확인할 내용                               |
| ---------------------- | ----------------------------------------- |
| `npm run typecheck`    | TypeScript 타입에 맞게 작성했는지         |
| `npm run lint`         | 코드·React Hooks 규칙을 지켰는지          |
| `npm run format:check` | 팀의 포맷 규칙과 일치하는지               |
| `npm run format`       | 코드·문서에 포맷 규칙 적용. 파일이 수정됨 |
| `npm test`             | 작성된 테스트를 한 번 실행                |
| `npm run test:watch`   | 코드를 수정할 때 테스트를 다시 실행       |

**현재는 테스트 설정만 있고 테스트 파일은 없습니다.** 따라서 `npm test`는 `No test files found` 안내와 함께 종료 코드 1을 반환합니다. 지금 단계에서는 테스트 실패 사례가 발견됐다는 뜻이 아닙니다.

기능을 작성하면서 대상 파일 옆에 `*.test.ts` 또는 `*.test.tsx`를 추가합니다. 단순히 개발 서버를 켜려는 경우에는 테스트 명령을 먼저 실행할 필요가 없습니다.

## 환경변수와 백엔드 연결 준비

환경변수는 **코드를 수정하지 않고 실행 설정을 바꾸기 위한 값**입니다. 기본 실행에는 `.env` 파일이 필요하지 않습니다.

설정을 바꿀 때 [.env.example](.env.example)을 같은 폴더에 `.env`라는 이름으로 복사합니다. 탐색기에서 복사하거나 운영체제에 맞는 명령 하나를 사용하세요.

```bash
# macOS / Linux
cp .env.example .env
```

```powershell
# Windows PowerShell
Copy-Item .env.example .env
```

| 설정                     | 의미                                                               |
| ------------------------ | ------------------------------------------------------------------ |
| `VITE_API_BASE_URL`      | 향후 브라우저 코드에서 사용할 API 기준 경로. 기본 `/api/v1`        |
| `API_PROXY_TARGET`       | Vite가 API 요청을 전달할 백엔드 주소. 기본 `http://127.0.0.1:8000` |
| `VITE_KAKAO_MAP_APP_KEY` | 향후 지도에 사용할 JavaScript 키. 지금은 비워 둠                   |

프록시는 브라우저의 요청을 백엔드로 전달하는 중간 연결입니다. 설정은 다음 흐름으로 준비되어 있습니다.

```text
브라우저에서 /api/v1/... 요청
  → 프론트 개발 서버가 전달
  → http://127.0.0.1:8000/api/v1/...
```

**현재 앱에서 API를 호출하는 코드는 없습니다.** 이후 API 기능을 작성할 때 백엔드를 별도로 실행하면 됩니다. 백엔드 실행 후 `http://localhost:8000/docs`에서 사용할 API와 요청·응답 형식을 확인할 수 있습니다.

`.env`를 수정하면 개발 서버를 종료했다가 다시 실행합니다. `VITE_`로 시작하는 값은 브라우저에 공개되므로 서버용 REST 키·AWS 인증 정보 등 비밀값을 넣지 않습니다. 실제 `.env`는 Git에서 제외되고, 이름과 작성 방법을 보여 주는 `.env.example`만 공유합니다.

| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `node` 또는 `npm` 명령을 찾을 수 없음              | Node.js 24 LTS 설치 후 터미널을 다시 열고 버전을 확인합니다.                                            |

| `package.json`을 찾을 수 없음                      | 프론트 저장소 폴더에서 명령을 실행했는지 확인합니다.                                                    |
| `vite` 또는 설치된 패키지를 찾을 수 없음           | `npm ci`를 먼저 실행합니다.                                                                             |
| `npm ci`에서 두 패키지 파일이 일치하지 않는다고 함 | 패키지를 수정한 사람이 `npm install`로 잠금 파일도 갱신했는지 확인합니다. 두 파일을 함께 받아야 합니다. |
| 제목과 기본 안내 문구만 보임                       | 현재는 정상입니다. 실제 서비스 화면과 기능은 아직 작성하지 않았습니다.                                  |
| `.env` 수정이 반영되지 않음                        | 개발 서버를 재시작합니다.                                                                               |
| API 요청 시 연결 실패                              | 기능 연결 단계에서 백엔드 실행 여부와 `API_PROXY_TARGET` 주소를 확인합니다.                             |

### `Port 5173 is already in use`가 나올 때

5173 포트를 다른 프로그램이나 이전 개발 서버가 사용 중이라는 뜻입니다. 이전에 실행한 터미널이 있다면 그곳에서 `Ctrl+C`로 종료한 뒤 다시 실행합니다.

기존 프로그램을 계속 사용해야 한다면 프론트 포트를 바꿀 수 있습니다.

```bash
npm run dev -- --port 5174
```

이때 접속 주소도 `http://localhost:5174`로 바뀝니다. 현재는 `strictPort: true`로 설정되어 있어 자동으로 다른 포트를 선택하지 않고 충돌을 알려 줍니다. 추후 지도 SDK를 연결했다면 변경된 주소도 허용 도메인에 등록해야 합니다.

## 빌드와 Git 공유

**빌드**는 개발 코드를 브라우저에 배포할 파일로 만드는 작업입니다.

```bash
npm run build
```

타입 검사 후 `dist/`에 HTML·JavaScript·CSS를 생성합니다. 빌드 결과를 내 컴퓨터에서 확인하려면 다음 명령을 실행합니다.

```bash
npm run preview
```

기본 주소는 `http://localhost:4173`입니다. 현재 빌드 결과에는 제목과 안내 문구만 표시됩니다. `preview`는 결과 확인용이고, 평소 코드를 수정할 때는 `npm run dev`를 사용합니다.

기획서의 배포 방향은 `dist/`를 S3·CloudFront에 제공하는 방식입니다. 개발용 프록시 설정은 배포 환경에 자동으로 적용되지 않으므로, AWS에서 `/api/*`를 백엔드로 전달하는 설정은 별도로 구성합니다.

| Git으로 공유                         | Git에서 제외                               |
| ------------------------------------ | ------------------------------------------ |
| `src/`, `public/`, 설정 파일, README | `node_modules/`, `dist/` 등 설치·빌드 결과 |
| `package.json`, `package-lock.json`  | 실제 `.env` 파일                           |
| `.env.example`                       | 개인 작업용 `agent/`, `AGENTS.md`          |

## 선택 사항 — Docker로 실행하기

**앞의 npm 방식으로 개발한다면 이 절은 건너뛰어도 됩니다.** Docker는 로컬에 Node를 설치하지 않고 같은 환경에서 실행하려는 경우의 대안입니다.

[Dockerfile](Dockerfile)에 Node **24.22.0**과 패키지 설치·빌드 방법을, [compose.yaml](compose.yaml)에 개발 서버 실행 설정을 작성해 두었습니다.

### 개발 서버 실행·종료

Docker Desktop을 실행한 뒤 프론트 폴더에서 다음 명령을 사용합니다.

```bash
docker compose up --build
```

처음 실행할 때 이미지를 만들고 `npm ci`로 패키지를 설치합니다. 접속 주소는 **http://localhost:5173**입니다. `src/`, `public/`, `index.html`은 로컬 파일과 연결되어 수정 내용이 반영됩니다. 패키지나 다른 설정 파일을 바꿨다면 같은 명령으로 다시 빌드합니다.

종료하려면 실행 중인 터미널에서 `Ctrl+C`를 누르고, 다음 명령으로 컨테이너와 해당 프로젝트 네트워크를 정리합니다.

```bash
docker compose down
```

npm 개발 서버와 동시에 실행하면 포트가 충돌할 수 있으므로 한 가지 방식만 사용합니다. 이 Compose는 프론트 서버만 실행하며 백엔드는 별도로 실행합니다.

### Docker 전용 환경변수

필요하면 `.env`에서 다음 값을 변경합니다.

| 설정                      | 의미                                                                         |
| ------------------------- | ---------------------------------------------------------------------------- |
| `FRONTEND_PORT`           | 내 컴퓨터에서 접속할 포트. 기본 `5173`. `5174`로 변경하면 접속 주소도 변경됨 |
| `DOCKER_API_PROXY_TARGET` | 컨테이너에서 접근할 백엔드 주소. 기본 `http://host.docker.internal:8000`     |

Docker Desktop에서 `host.docker.internal`은 호스트 컴퓨터를 가리킵니다. Linux에서 백엔드가 호스트의 `127.0.0.1`에만 공개돼 있다면 컨테이너가 접근할 수 없으므로, npm 방식으로 프론트를 실행하거나 접근 가능한 내부 연결 주소를 따로 맞춥니다.

환경변수를 변경했다면 `docker compose up --build`를 다시 실행합니다.

<details>
<summary>Docker로 정적 파일만 빌드하기</summary>

```bash
docker build --target export --output type=local,dest=dist .
```

내 컴퓨터의 `dist/`로 결과물을 내보냅니다. Dockerfile의 마지막 단계는 정적 파일 내보내기용이며 운영 웹 서버를 실행하는 단계가 아닙니다.

Docker 빌드는 `.env`를 읽지 않습니다. 향후 지도용 JavaScript 키 등 공개 빌드 설정이 필요하면 `--build-arg VITE_KAKAO_MAP_APP_KEY=값`을 추가합니다. 서버 비밀키를 전달하는 용도로 사용하지 않습니다.
